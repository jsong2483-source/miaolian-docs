# 妙恋畅语项目计划书（MVP V1.0）

> 项目：妙恋畅语 ｜ 文档版本：v2.15（产品 MVP V1.0） ｜ 立项：宋佳兴 ｜ 评审与修订：阿砚 ｜ 2026-10-25

## 1. 项目定位

**妙恋畅语**是一款面向成年人恋爱沟通场景的移动应用。用户建立心动对象档案、粘贴聊天记录，系统结合人物信息、关系阶段和聊天上下文，检索合适模板并生成可编辑的回复建议，同时呈现关系进展与下一步建议。

## 2. MVP 目标

- 让用户在数分钟内完成首个对象档案和一次聊天分析。
- 为指定的对方消息生成三条自然、尊重且可编辑的回复建议。
- 将重要互动整理为关系阶段、事件时间线和下一步行动。
- 用户可控制、导出和删除其数据；应用不会自动读取或代发第三方聊天消息。

## 2.1 硬性约束（不可去掉的需求）

这两条由立项人于 2026-10-25 定为第一优先级。它们会直接影响技术选型与页面结构，任何方案都不得绕过。

### 约束一：必须能接大模型，采用 BYOK（用户自填 Key）

- 首期接入 **DeepSeek API**，Key 由用户自己填写、自己保存。
- Key 只存在设备本地加密存储（`flutter_secure_storage`），**不上传、不写入日志、不进代码仓库、不经过我们的服务端**。
- 请求由客户端直接发往模型服务商。**我们的服务器只看得到结构化结果，看不到 Key，也看不到完整原文。**
- 未填 Key 时降级为「只用模板库、不做生成」，不弹错误、不逼用户去填。
- 设置页必须提供：录入 Key、检测连通性、清除 Key、查看当前用的是哪个模型。

**为什么这条是正确的：** 服务器不持有用户的 Key，就没有"泄露一整批 Key"的可能，也没有"我们拿用户的钱跑推理"的嫌疑。**安全边界从"信任我们"变成"信任你自己的手机"。**

### 约束二：每个对象必须有「攻略面板」

- 用户为每个心动对象建立独立档案，**档案必须有一个集中查看的面板**，不能散落在多个页面里靠翻找。
- 面板是产品的核心屏，也是用户每次打开 App 第一眼要看的东西。
- 面板至少要同时承载：当前阶段与变化趋势、四个关系维度及其证据、边界状态、下一步该做什么、对方的关键信息（兴趣/禁忌/重要日期）、事件时间线。
- **判据：用户打开面板 10 秒内，能回答"现在什么局面、我下一步该做什么"。** 答不上来就是面板设计失败。

## 3. 目标用户

- 希望更自然表达、改善恋爱沟通的成年人。
- 正在认识、暧昧、恋爱或尝试修复关系的用户。
- 希望记录关系重要信息、事件与个人感受的用户。

## 4. 核心功能范围

| 模块 | MVP 功能 |
| --- | --- |
| 心动对象 | 新建、编辑、归档人物档案。 |
| 人物档案 | 称呼、头像、关系状态、兴趣、禁忌、重要日期、备注与沟通目标。 |
| 聊天导入 | 用户粘贴文本、标记“我/对方”、提交分析。 |
| 聊天分析 | 提取话题、互动信号、关系阶段、边界提示和下一步建议。 |
| 回复助手 | 基于上下文和档案生成温柔、幽默、真诚、克制等三条候选回复。 |
| 关系进展 | 当前阶段、可解释维度、重要事件和时间线。 |
| 模板库 | 内置与收藏模板，支持按场景、语气和语义检索。 |
| 数据控制 | 删除聊天、对象和账户资料；支持个人数据导出。 |

## 5. 暂不纳入 V1

- 自动读取、自动发送微信、短信或其他第三方聊天内容。**包括无障碍服务读屏、解密微信电脑版备份文件——这两条不是"以后再说"，是永不触碰：违反平台协议、必然封号，且隐私上无法自证清白。**
- 社交匹配、公开社区和对象资料共享。
- 订阅付费、广告和积分商城。

> 变更记录：**"聊天截图 OCR"已从本清单移除，升为 V1 必做项。** 原因见 `01-文档/第一版-聊天导入方案-v2.13.md`——微信/抖音都不支持整段复制，截图是一、二号入口里唯一稳定可用的那个。移出清单不代表它便宜，它代价很高，只是没有它就没有输入。

## 6. 核心流程

```text
新建对象档案
  → 导入聊天记录（截图识别 / 粘贴文本）
  → 确认每条是「我」还是「对方」
  → 分析互动信号与当前关系阶段
  → 检索相关回复模板
  → 生成三条可编辑回复
  → 用户复制并自行发送
  → 记录事件、更新下一步计划
```

> 第一步为什么是两条路：微信、抖音都只能单条复制，**没有"导出整段对话"这个功能**。截图识别是主路径，粘贴是保底——保底这条永远不能删，因为 OCR 会因为深色模式、表情包、马赛克失效。
>
> 第三步也**不能省**：OCR 一定会有错，而错在"谁说的"上，整张面板的结论就反了。宁可让用户花 20 秒扫一眼，也不要假装我们都对。

## 7. 关系进展系统

### 关系阶段

1. 初识破冰：自然开启话题，避免密集追问。
2. 熟悉建立：积累共同话题与生活细节。
3. 暧昧升温：适度表达好感，创造轻量邀约。
4. 关系确认：沟通期待、节奏与边界。
5. 稳定经营：维持日常连接、处理冲突、记录重要时刻。
6. 需要空间：出现拒绝或压力信号时，尊重边界、减少推进。

### 关系温度：状态 + 变化 + 依据

产品在这一块的主线目标是**让用户感知变化**，不是给关系打分。所以每个维度用三层表达，缺一层都不算做完：

| 层 | 回答的问题 | 输出形式 | 示例 |
| --- | --- | --- | --- |
| 状态 | 现在大概在什么位置 | 三档文字：较低 / 中等 / 较高 | 熟悉度 · 较高 |
| 变化 | 跟上次比往哪走了 | 三个词：升温 / 基本没变 / 转冷 | 互动热度 · 升温 |
| 依据 | 凭什么这么判断 | 一句可点回原文的话 | 她主动开启话题 3 次，上周 1 次 |

维度本身仍然四个：熟悉度、互动热度、信任与舒适度、线下推进。

规则：

- **全应用不出现任何百分比和进度条。** 这条被推翻过三次，每次都记在这里：v1.0 四条进度条 → v2.1 改三档文字（理由：数值没有参照系）→ v2.5 按立项人要求改回百分数（理由：数字更抓人）→ **v2.15 全部改回文字**。
  这次的理由和第一次不同，也更硬：**数字会让整个界面变成数据面板。** 一屏出现四个百分数、四条曲线、一个趋势角标，产品的注意力就从"她现在到底怎么想"滑到"这个数怎么没涨"。恋爱沟通工具一旦长得像股票软件，用户就开始盯盘，而不是沟通。
  代价也要写清楚：**文字的分辨率比数字低。** 用户没法看出"72 变 75"，只能看出"中等到较高"。这是刻意的——关系本来就不是连续可测的量。
- **变化必须有基线。** 每次分析与上一次快照对比。没有基线时只写状态，不写"升温/转冷"。
- **每个状态都必须挂一条能指回输入的证据。** 指不回去的判断不显示，宁可空着。
- **证据以原图为准，OCR 文本不得冒充原文。** 截图识别出来的文字可能有错字，如果把它当"原文"展示给用户，我们就是在伪造证据。规则是：文字只在后台喂模型（错一个字不影响理解），**证据层永远显示原截图的裁剪块 + 高亮框**。原图分析完即删，只留被引用的那一小块。
- 阶段变化的方向要保守：**升级需要多个信号，降级一个信号就够**。
- **颜色只承担三种含义，不许扩张。** 主色（玫红）= 品牌与"升温"；绿 = 状态正常；红 = 风险（边界警示、越界回复）。**"转冷"不给任何鲜艳颜色**，用冷灰 + 文字表达。
  这条推翻了 v2.7 的股市约定（升温红 / 转冷绿）：那一版撞了两个车——绿既表示"转冷"又表示"边界正常"，用户会把转冷读成安全；而且红既表示"升温"又表示"警示"，同一个颜色一会儿是好事一会儿是危险。
- **首页不放曲线。** v2.9 曾在首页挂过四维折线，v2.15 撤掉。首页只回答一件事：**现在这段关系是什么局面，今天能做什么。** 要细节就进关系面板，那里也不给图，给四条文字判断。

### 边界状态

边界不是第五个并列维度，而是一个**优先级高于所有推进建议**的开关：

- 检出回避、拒绝、明确不适 → 邀约/推进类模板强制不可用，下一步建议整体切换为「暂不推进」。
- 边界只能由"有信号"触发，不能因为"没看到信号"就默认安全。
- 这条规则必须落在代码逻辑里（检索前硬过滤），不能只写进提示词。

系统不把四个维度合成一个"好感度总分"展示——四个判断各自独立，没有总分，没有排名，也没有及格线。也不把聊天数据包装成确定的人格标签或绝对结论。

## 9. 技术方案

| 层级 | 推荐方案 |
| --- | --- |
| 移动端 | Flutter + Dart，覆盖 Android 与 iOS。 |
| 后端 | Python FastAPI，提供身份、档案、分析与回复接口。 |
| 数据库 | PostgreSQL，保存用户、对象、事件与分析结果。 |
| 语义检索 | pgvector，用于匹配回复模板。 |
| AI 能力 | **BYOK 直连 DeepSeek**（`https://api.deepseek.com`，OpenAI 兼容格式，模型 `deepseek-chat`），Key 存本地。 |
| 聊天识别 | **本地离线 OCR**：移动端 ML Kit（`google_mlkit_text_recognition`，免费、支持中文、返回坐标框）；Windows 用系统 OCR 或 PaddleOCR。 |
| 后续扩展 | Redis 用于限流/队列；对象存储保存用户主动上传的头像。 |

### 聊天记录从哪来（这一节是地基）

**微信和抖音都不支持"整段对话复制"。** 微信只能长按复制单条；多选之后只能转发到微信内部（好友、文件传输助手、收藏），合并转发产出的是"聊天记录卡片"，不是文件，第三方打不开。

微信的分享能力是单向的：**App → 微信开放，微信 → App 不开放。** 这是产品上的封闭设计，不是技术问题。

所以入口只有两条，都必须做：

| 入口 | 地位 | 说明 |
| --- | --- | --- |
| 截图识别 | 主路径 | 唯一稳定可用的通用出口 |
| 粘贴文本 | 保底 | 单条复制拼起来，或手打。OCR 失灵时唯一退路，永远不能删 |

三条红线，永不触碰：**解密微信电脑版备份、Android 无障碍读屏、云端 OCR 上传截图。** 前两条违反平台协议（腾讯 2024、2026 两次点名打击该类工具），第三条违背 BYOK 的"数据不出设备"。

OCR 的真实难点不在认字，在：① 说话人归属（按文本块横坐标分左右）；② 跨图去重与排序；③ 时间戳解析；④ 错字毁掉证据（见 §7 的"证据以原图为准"）；⑤ 截图里混进了对方的头像昵称或别人的对话。

### 字体

**全应用只用一种中文字体：思源黑体（Noto Sans SC）。** 不加第二套，不加衬线，不单独换数字字体。

v2.8 曾经定过三档（正文思源黑体 / 数字 Inter / 阶段名思源宋体），v2.15 收成一种。理由：三套字混排会让页面气质分裂——标题是文艺的、数字是工程的、正文是工具感的，用户说不出哪里怪，但就是"不像一个东西"。

**字号只有四档，不许临时加第五档：**

| 用途 | 字号 | 说明 |
| --- | --- | --- |
| 页面标题 | 22px | 每屏只有一个 |
| 区块 / 卡片标题 | 17px | |
| 正文 | 15px | 手机正文不低于 14px |
| 辅助说明 | 12px | 下限，不许再小 |

v2.8 有一批 11px、11.5px 的小字，v2.15 全部抬到 12px 以上。**小字不是精致，是难读。**

字重回退说明：思源黑体有真 Medium，`font-weight: 500` 不会跳粗。若 CDN 加载失败退回微软雅黑，雅黑只有 400/700，500 会被渲染成粗体——**这是原型在断网时的降级表现，不是设计值**。

落到 Flutter 上：**移动端不用打包任何中文字体**。iOS 自带苹方、Android 自带 Noto Sans CJK，都是同系高质量字，直接指系统字体即可。这一版取消了 Inter，assets 里一个字体文件都不需要。

Web 原型（`02-原型/`）用 CDN 加载三种字重，断网会退回系统字体——**这是原型的问题，不是产品的问题**，App 里不会出现。

### 视觉规范（v2.15 重写，此前的版本全部作废）

v2.12 那一版同时用了四种设计语言：恋爱氛围（粉紫渐变）、数据仪表盘（曲线 + 百分比）、玻璃拟态（半透明模糊 + 柔光球）、游戏攻略（巨大的「攻」）。结果不是"丰富"，是**每个组件都在争注意力，没有一个主角**。下面是重新定的规矩，**后续任何一版都不许私自破例**：

| 项 | 规定 | 为什么 |
| --- | --- | --- |
| 背景 | 纯色 `#f7f6f8`，**不许有渐变、光斑、模糊圆** | 柔光球是玻璃拟态的标志，它让每个元素都"浮着"，等于没有层级 |
| 卡片 | 白底 + 1px 浅边框 + 圆角 16，**无阴影、无模糊** | 阴影一多，所有卡片等重，重点卡片就消失了 |
| 卡片数量 | **一屏最多 2–3 个卡片**，其余用列表 | 满屏卡片 = 满屏塑料片 |
| 列表 | **普通列表不套卡片**，用 1px 分隔线 | 对象列表、模板、回复候选、维度，全部是列表 |
| 圆角 | 卡片 16 / 按钮 12 / 缩略图 8 / 标签胶囊 | 圆角越大不等于越精致。全部圆 = 软塌、像儿童应用 |
| 间距 | 只用 4 / 8 / 12 / 16 / 24 / 32 六档 | 靠临时 `height: 14px` 拼出来的页面，局部都对、整体没有呼吸感 |
| 颜色 | 主色一种（玫红 `#c9355f`）；绿=正常；红=风险；**没有紫色** | 粉紫红绿橙青同时出现，语义必然打架 |
| 底部导航 | 5 个入口，**图标 + 文字同规格**，无凸起按钮 | 中间一个大「攻」，把产品做成了追人闯关工具 |

**一条判断标准**：如果一屏里有两样东西一样显眼，那就没有主角，重做。

### BYOK 的工程细节

```text
用户第一次使用生成功能
  → 引导填写 Key（设置页）
  → 本地连通性检测（发一条最小请求）
  → 存进 flutter_secure_storage
  → 之后每次请求：客户端 → DeepSeek
  → 只把返回的文本落库，不落 Key、不落完整 prompt
```

三条硬要求：

1. **Key 不进日志。** 打印请求体之前必须脱敏，否则一个 `debugPrint` 就能把 Key 写进 crash 日志。
2. **Key 不进仓库。** 不要写进任何 `.dart` 常量、不要提交 `.env`。
3. **未填 Key 必须能正常使用**：只走模板库，界面提示"填入 Key 后可生成"，而不是报错阻断。

### 为什么不会慢（延迟预算）

立项人问过："那么多文字处理，会不会速度太慢。"先把账算清楚——**慢的从来不是我们的代码，是大模型在思考。**

| 环节 | 耗时 | 在哪 | 能不能省 |
| --- | --- | --- | --- |
| 首页曲线 / 面板渲染 | < 30ms | 本机 | 已是最快 |
| 截图解码 + OCR（10 张） | 2–4s | 本机 | 降采样能砍一半 |
| 说话人归属 + 去重 + 排序 | < 50ms | 本机 | 纯字符串，忽略不计 |
| 边界判定 | < 20ms | 本机规则 | **故意不给模型** |
| 关系分析（DeepSeek） | 首字约 1.5s，全长 4–8s | 网络 | 流式 + 拆调用 |
| 三条回复（DeepSeek） | 与上一步**并行** | 网络 | 并行，不叠加 |

总感知约 10 秒，其中 8 秒在等模型。**我们自己那部分加起来不到 1 秒。**

五个具体手段：

1. **边界判定不给模型，写成规则。** 关键词 + 拒绝模式匹配，20ms 出结果。这既是性能选择，也正好满足 §7 那条"必须落在代码里，不能只写进提示词"。
2. **拆成两次调用，并发发出。**"分析"和"回复"用同一段对话、互不依赖，同时发，总时延取 max 而不是 sum。
3. **模型只输出编号，不输出原文。** 本地把 200 行对话压成 60 行信号表再喂，模型返回"证据 #17"而不是复述原句。省 token、快一倍，还顺手解决了"模型编造原文"和"OCR 错字当证据"两个问题。
4. **流式 + 分块亮相。** 用户感知的不是总耗时，是多久看到第一个字。先出阶段，再出四个维度，再出依据——不要等全算完才渲染。原型里点「开始分析」会看到这个过程。
5. **只算增量。** 同一对象只分析新增的那几条消息，不重算 30 天。固定不变的提示词和模板库放最前，对话放最后，提高 DeepSeek 的上下文缓存命中率。

一条容易踩的坑：**OCR 和图片解码不能放主线程。** 10 张 4K 截图在 UI 线程解码会直接卡死。Flutter 里解码丢给 isolate，并先把长边降到 1500px——OCR 不需要 4K。

### 一个必须先知道的坑



**Flutter 编译到浏览器（Edge/Chrome）时，直连第三方 API 会被浏览器 CORS 拦掉。** 这不是代码写错，是浏览器的安全策略，DeepSeek 也没有为网页请求开放跨域。

后果：**阶段 0 用 Edge 跑起来，只能验证界面，验证不了大模型链路。** 想真正跑通 API，必须跑在 Windows 桌面或 Android 设备上。

所以排期上要分清：

| 目标 | 最低要求 |
| --- | --- |
| 看界面长什么样 | Flutter + Edge，今天就能有 |
| 跑通 BYOK 链路 | Flutter + Windows 桌面（需 Visual Studio C++ 组件）或 Android 真机 |

### AI 处理链路

```text
用户输入
  → 长度限制与不必要标识清理
  → 安全/边界信号检测
  → 提取结构化上下文
  → pgvector 检索相关模板
  → 按边界状态硬过滤模板（检出边界时移除邀约/推进类）
  → 大模型结合模板生成候选回复
  → 安全检查与格式化
  → 返回可编辑结果
```

## 12. 验收标准

- 用户可建立、编辑、归档和删除对象档案。
- 关系判断不出现任何百分比、进度条或单一总分；每个维度给的是"较低 / 中等 / 较高 + 一句可回溯到原文的依据"。
- **用户填入自己的 DeepSeek Key 后，能完成一次真实的生成请求；Key 不出现在日志、代码和任何服务端存储里。**
- **未填 Key 时，应用仍能正常打开与浏览，只是不给生成结果。**
- **每个对象都有攻略面板，打开 10 秒内能说清"现在什么局面、下一步做什么"。**
- 粘贴聊天内容后可获得可编辑分析、阶段建议与三条回复候选。
- **截图导入后能逐行改正"我/对方"，且每条证据展示的是原图裁剪块、不是识别出来的文字。**
- 回复建议能结合档案、目标与语气，并给出匹配依据。
- 用户可删除与对象相关的记录。
- 应用没有自动读取、自动发送或暗中共享聊天内容的能力。

## 13. 隐私与安全边界

- 仅处理用户有权提供的聊天内容，并提醒尊重他人隐私和意愿。
- 原始聊天文本默认分析后删除；是否保留由用户明确选择。
- 使用加密传输，敏感数据加密存储；支持查看、导出和删除。
- 不鼓励骚扰、威胁、道德绑架、跟踪或规避明确拒绝。
